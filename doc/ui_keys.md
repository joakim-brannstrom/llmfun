# llmfun keys

Generated by `tools/gen_ui_keys.sh` from three sources, never edited by hand:

- the binding table (`cpp_tui/model/keymap.cpp`: every row, its region and its other
  entry point);
- the `Esc` chain, whose steps are `model::resolveEscape()`'s code;
- the rail's row keys (`cpp_tui/model/rail_keys.h`, the table `views/rail.cpp` reads its
  characters from).

`./test_ui_keys` compares this file with those sources, so a binding, a chain step or a
row key that changes without regenerating it fails the build. The prose paragraphs are
reviewed by hand; the tables are generated - except the Composer keys rows that repeat
`Up`/`Down` and their `Ctrl` aliases, which are prose and can drift from the registry row
above them.

**What this document covers.** The registry rows, the `Esc` chain and the rail's row
keys. It does not list the character keys a surface reads for itself - the Raw Log's
`f`/`p`/`/`/`y`, the inspector's `[`/`]` and its hovered `m`, the settings sheet's list
keys, the palette's, and the help page's `?` (the terminal delivers no key event for a
printable character, so `Shift+/` is a row for the pixel profile and a typed character
for the grid) - because those literals live at their call sites rather than in
one table (the rail's are the ones lifted into `rail_keys.h`).

One binding per row; `where` is the region that owns the keyboard. A chord with no
modifier never fires while a text field has the keyboard, and an overlay is a keyboard
trap: while it is open only its own rows (and the ones repeated for it) fire.

## Esc

`Esc` is not a registry row: its action depends on the run and the input, and the order
lives in one function (`model::resolveEscape`). One step per press. The steps below are
derived from that function - each state is asked of the resolver, so a reordering shows up
here - and the sentence after each name says what the step means:

1. `CloseOverlay` - close the topmost overlay (help page, palette, settings sheet, Raw Log, inspector panel, rail panel);
2. `ExitFocusMode` - leave focus mode (the side panels and the bar come back; the draft and the run are untouched);
3. `CancelRun` - cancel the running agent (the same request `/stop` makes; partial output is kept);
4. `ClearInput` - clear the composer's draft;
5. `Blur` - release the keyboard;

A view that owns a press of its own (the rail's rename box, its search field, its row
menu) spends it before the chain sees it, and the frame's chain stands down for that
press.

## Rail row keys

The rail reads these as characters, not as registry rows: they act on the row the user
aimed at (the pointer's row, or the keyboard-focused one), and a collapsed rail's strip
carries none of them.

| key | action |
| --- | --- |
| `/` | focus the search field (from anywhere except the composer) |
| `m` | open the row menu |
| `r` | rename the row |
| `d` | delete the row, in one press (the guard is the aimed-at row) |
| `p` | pin or unpin the row |
| `Enter` | in the search field: select the best match |

## Composer keys

| key | action |
| --- | --- |
| `Enter` | newline in the draft - the terminal delivers `Shift+Enter` and `Ctrl+Enter` as the same byte (plan/key_gate.md §3), so `Enter` cannot send; the composer's `Send` does |
| `Up` / `Ctrl+Up` | recall the previous query |
| `Down` / `Ctrl+Down` | recall the next query |
| `/` on an empty line | open the palette's command entry |

## Delivery

A row exists only where the chord is actually delivered. Three consequences are worth
knowing before a key looks broken:

- the terminal does not deliver `Ctrl+I`, `Ctrl+5` or `Ctrl+6` (byte 9 is `Tab`, and
  `0x1D`/`0x1E` are unmapped). The inspector is reached there through the palette rows,
  the top bar's `Settings` entry and the panel's own `[`/`]` tab keys;
- `Ctrl+Shift+L` arrives as `Ctrl+L` in the terminal (the Shift is lost), so the grid's
  paths to the Raw Log are `/rawlog`, the palette's Developer row and `--debug-ui`;
- `Shift+/` is `?`, and the terminal delivers it as that typed character rather than as a
  key, so the help page opens there from the character (`views/shell.cpp` reads it) and
  from the chord in the pixel profile.

`Ctrl+C` is not bound at all: the terminal turns it into `SIGINT` before the UI reads it,
and in the GUI it is the text field's copy chord.
